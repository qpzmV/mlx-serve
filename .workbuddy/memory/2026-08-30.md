## [vqmm] NAX verify lane 日志的来源（用户追问"是硬件返回还是代码变量"）

- **全是代码里的变量，非硬件直接返回**：
  - `bits` / `group_size`：源自 `config.json` 的 `quantization.bits` / `group_size`（用户 4bit gs32），经 `config.quant_bits`/`config.quant_group_size` → `QuantParams{bits,group_size,mode}`（transformer.zig:4962-4964）→ `verifyQmm(s,x,w,sc,bi,bits,group_size)`（transformer.zig:1338/24486）→ `runVerifyQmmNax(...bits, group_size ...)`。
  - `M`=m：activation 行数，代码算的（`m` 累乘 x 的各维，line 1360-1361）。
  - `K`/`N`：权重张量 shape 推导（line 1359/1364），K=x最后一维，N=w第一维。
  - `min_m`：`naxMinMForBits(bits)`（transformer.zig:2030），bit 数查表。
- **真正"硬件相关"的部分只有一个**：`nax_on = naxLaneEnvEnabled() and verifyQmmNaxAvailable()`（line 1368）。 `verifyQmmNaxAvailable()`（line 1610）探测 M5 NAX 是否可用 → 决定要不要走 NAX lane。**NAX 通道本身是否开启靠这个探测；但日志里打印的值（4-bit/M=8/gs=32）全部是模型配置 + 张量形状，不是硬件返回。**
- 结论：`M=8` 是运行时 activation 行数（投机验证一次取 8 个 token），`gs=32` 是模型自身的量化粒度，`4-bit` 是模型精度。这些不是你的硬件"报告"的值，是引擎拿你的模型配置算出来、打印给你看的。

## 内存优化 plan（用户问"不提速怎么降内存"，只读分析 2026-08-30 晚）
### 关键结论：权重即墙
- Qwen3.8-Flash-Next (125B MoE, 4bit) 权重 ~105.4GB（实测日志），绝对大头，**运行时无法压缩**（mlx-serve 不做专家 offload/SSD 流式，那只有 ds4/`--ssd-streaming` 支持，MLX 引擎忽略）。
- 用户模型 `config.json`: `num_experts=512, num_experts_per_tok=10, full_attention_interval=4, head_dim=256, kv_heads=2, hidden=2560, moe_inter=640, ple_layer_ids=[2], mamba_ssm_dtype=float32, quantization{bits:4,group_size:32,affine}`。
- 48层中仅 12 层 full_attention 缓存 KV（attnCacheLayerCount，model.zig:709）。非MLA：`dense_per_tok = 12*2*(2*256)*2 = 24576 B`。
- `kvBytesPerTokenAtBits`（server.zig:3015）：`dense*(2*bits+1)/32`。→ 16b 24KB/tok，8b 12.75KB/tok，4b 6.75KB/tok。**KV cache 在 64K ctx 下 8b≈0.8GB、4b≈0.42GB，全模型微头。**

### 运行时能动的配置（按收益排序）
1. **`--kv-quant 8`→`4`**（当前 8b 0.8GB@64K→0.42GB，省 ~0.4GB；或 `turbo4`）——收益小。
2. **`--ctx-size` 已 64K（模型 max 262144），再降省 KV**：64K→32K 省 0.4GB，→16K 省 0.6GB。
3. **`--prefix-cache-mem` 默认 2GB**：降成 1GB/512MB 或 `off`（省 0.5-2GB），伴随 `--prefix-cache-entries 8`→`0`（关 SSM 检查点捕获，对 64K 内场景影响小）。
4. **`--max-resident-mem`（auto=80% wired=~94GB）**：显式设小能让 auto context sizer + prefill chunk 更激进地贴近权重，但收益是把"预留"还给 OS，不是省实际驻留。
5. **`--prefill-chunk` 已因内存压力降到 4096**（日志），再降 2048/1024 省瞬态，主要影响长 prompt 首token，对峰值有小帮助。
6. **`--no-warmup-eager`**：省启动时峰值，但首token 变慢。
7. **`MLX_SERVE_CACHE_LIMIT`**（buffer pool cap 已压到 8GB / 124GB→8GB，main.zig applyMlxCacheLimit）。再降会伤性能（步间 buffer 复用减少）。
8. **`--max-resident-models 3`**：若只跑这一个模型，无重叠收益。

### 超只读范围的（需改模型/代码，仅记录）
- `mamba_ssm_dtype: float32`（SSM 状态层用 f32，config 固定）→ bf16 省状态内存，但属模型层改动。
- 换更低位宽权重（2bit/更激进的量化）→ 重新下载/量化，非配置项。
- MLX 引擎无专家 offload。

### 结论
- 运行时能压缩的空间（KV+prefill+buffer pool 预留）合计 **~3-6GB**，相对 105GB 权重杯水车薪。
- **真正降低峰值的杠杆是换更小模型或更低 bit 权重**；配置项只能在"权重必须常驻 105GB"前提下抠出几 GB 余量。

## 用户问"能不能像ds4那样streaming，省掉105GB权重"（2026-08-30 晚，只读分析）
### 结论：MLX 引擎做不到专家级 SSD 流式，这不是"改个开关"能解决的
- `--ssd-streaming` 帮助文本明确写 **"Ignored by the MLX + llama.cpp engines"**（main.zig:276），只在 ds4/DeepSeek-V4 引擎生效。用户模型 MLX 引擎直接忽略。
- **ds4 的 ssd_streaming 是 C 侧原生命令**：`EngineOptions.ssd_streaming/ssd_streaming_cache_experts/ssd_streaming_cache_bytes/ssd_streaming_full_layers`（ds4_ffi.zig:122-137），直接从文件 mmap/读盘，只缓存最近 N 个专家、warmup 按需 preload——这是 ds4 引擎架构自带的。
- **MLX 引擎没有这个挂点**：专家权重加载走 `getLayerWeightOpt(weights, ...)` 从 tensormap 一次性拉出来变成 `mlx_array`（transformer.zig:18526-18888），512 专家全量绑定为图常量，decode 时 gather_qmm 只在已驻留张量上做行选择。**没有"只驻留最近专家、其余读盘"的路径。**
- 唯一沾边的是 `--ane-prefill`（transformer.zig:15876 起）：把 prefill 的部分 MLP / GDN 层 offload 到 ANE，还是全量常驻，只是换个计算单元，不是省 105GB。
- 唯一真 mmap 的是 qwen4 的 PLE n-gram 表（transformer.zig:6263/6887，`NgramTable` mmap）——但那只有 1.6KB/token，占权重的零头。

### 想真正省掉 moe 权重的几条路（都超"只读不改代码"范围，仅记录）
1. **上游 MLX 加 expert offload / ssd streaming 支持**——大工程，MLX 社区目前无此设计。
2. 换 ds4 引擎能跑的 DeepSeek-V4-Flash 同级别权重（用上现成 ssd_streaming）。
3. 换更小/更低 bit 的 Qwen 模型（2bit / 更激进量化）。
4. `mamba_ssm_dtype f32→bf16`（config 改动，省 SSM 状态内存，不省 MoE 权重）。

### 给用户的一句话
"就像笔记本一样，这段"权重"是你必须背在身上的 105 公斤；ds4 是自带'行李箱能有轮子只装必需品'的先天设计，MLX 引擎没有这个轮子。代码层面加这个轮子是大工程，不是启动参数能解决。"

## 【重要纠错】MLX 专家 offload 并非"无此设计"——之前用 GitHub API 搜到 0 条是**限流误导**（2026-08-30 晚，用户让查证后纠正）
### 我之前错误说"MLX 目前无此设计"，是错的。证据：
1. **ml-explore/mlx #2878**（feature request "On-disk out-of-core streaming of model weights for low-RAM inference"，2025-12-06 Isaina 开）——**已被社区认真推进**，权威 TL;DR：
   - **"transparent bigger-than-RAM streaming is impossible on Metal"**（实测，非猜测），两大阻碍：① Metal 在首次 kernel use 时会把整个 bytesNoCopy buffer 全量 wire（一个 3MB 的单专家 gather 会把整个 1.2GB 张量 fault 进来）；② wired ceiling 会把 mapped buffers 计入（一个 217GB 模型在 128GB 机器上碰到 ~112GB 时死于 kIOGPUCommandBufferCallbackError-OutOfMemory）。
   - 但 **两个"有用的替代方案"都 work，其中一个是 PR #4249**：
     - **mapped views（#4249）**：weights ≤ wired ceiling 时，26B MoE 4bit→132 tok/s，8bit→100.2%（相对 resident），bf16→101.2%；~1-2s 零拷贝加载；page cache 跨重启存活。但**注意：mapped views 不减少 generation-time 内存**（触及的权重照样全量 wire），它是"residency-control + load-economics"原语，不是内存减法器。
     - **expert slot-cache（应用层）**：这是**真正省内存**的那层。实测 Qwen3-235B (132GB)→15.5 tok/s@86GB wired；Qwen3.5-397B (218GB)→8.8@84GB；GLM-5.2 (418GB)→1.7@89GB。
   - 实测 null：专家路由在三个模型家族上都是 **LRU 命中率差**（LFU≪LRU；clairvoyant OPT 只多 +0.07 hit）——决定一切的是**容量和抓取带宽**，不是路由算法。
   - 若 MLX 想要（除 PR 外）一个小改动：**aligned save_safetensors**——现在张量落在非对齐 offset 上，强制做一次 repack 之后才能被 map。
2. **huckiyang/mlx-moe-offload（MIT，2026-07 活跃）**——社区 drop-in 项目，**回答 ml-explore/mlx-lm#1438**（"stream MoE experts from SSD to run models bigger than unified memory"）：
   - `patch_model()` 替换 mlx-lm 的 `SwitchGLU`；`repack` 把 stacked/per-expert 专家切成 per-expert mmap store；`OffloadedSwitchGLU` 只算 router 选中的专家。
   - 适用任何用 SwitchGLU 的 mlx-lm MoE：Mixtral、Qwen3-MoE、DeepSeek-V3、GLM-MoE…
   - 旗舰 demo：Inkling-2bit（975B总/41B激活/256专家/layer，~315GB）在 **192GB Mac** 能跑（RAM=resident(~35GB)+hot-expert cache；cold 专家在 SSD）。M4 Max 64GB 也能慢速跑。
   - caveat：**速度被路由命中率+SSD带宽决定**；uniformly-routed（Inkling）缓存差；skewed-routing 缓存好；decode 最差 ~0.03-0.4 tok/s（当 store 不放 page cache）；**prefill 必须 chunked**（否则 lazy 全量 forward 会 pin 所有专家 OOM）；**jetsam 风险**（64GB 跑 315GB 模型，长多模态会被 jetsam kill）。
   - 这是 **Python/mlx-lm 生态** —— 对 mlx-serve 的 **C++/Zig 引擎无法直接用**，但证明"MLX 生态做 expert-offload 是可行路线"。

### 对用户的实际意义（修正后的诚实结论）
- **MLX 官方**：#2878 仍 open，核心结论是"透明的 bigger-than-RAM streaming 在 Metal 上 impossible（有实测两座墙）"，PR #4249 是零拷贝 mapped-view 原语（**不省 generation 内存**）。真正省内存的 expert slot-cache 是**应用层**（外挂）做的，不是 MLX 内核。
- **社区**：mlx-moe-offload 证明 expert-offload 能在 MLX 生态跑通，但只能用于 Python/mlx-lm，且 Inkling（uniform routing）很慢（0.03-0.4 tok/s）。对 Qwen 这种 diverse routing 可能更快，但 mlx-serve 是引擎实现，接不了 Python patch。
- **对 mlx-serve**：想在 mlx-serve（C++/Zig 引擎）里加 expert-offload，要么等 MLX 内核支持，要么在 mlx-serve 自己做一个类似 "应用层 expert slot-cache" 的 C++ 实现——这是新工作，不是配置项。若只想省内存跑旧模型，换 ds4 引擎（带原生 ssd_streaming）或更低 bit 权重仍是更快的路。

## slotstream 评估：能否直接跑本地 Vontra 权重（2026-08-30 晚，只读评估，未执行任何命令）

用户问：`/Users/robin/workspace/1@inference_engine/slotstream` 能跑 `~/.mlx-serve/model(s)/` 下的 qwen3.8 flash 吗。

### 结论：**能跑，且不用重下 104 GB**。`--model` 传本地目录即可。

**证据链（可复现）**
- `Sources/slotstream/main.swift:22-24` `--model` help 明写 "Model name or **directory**"。
- `Sources/slotstream/Pull.swift:36-46` `ModelLocator.resolve()`：路径存在则直接返回，**绕开 sha256 清单**。
- `main.swift:76-85` `ensureWeights()`：`guard model == PinnedModel.name || dirName else { 只检查 config.json 存在就 return }` —— **显式路径不触发下载/校验**。
- `Sources/SlotstreamCore/Checkpoint.swift:CheckpointIndex.init(dir:)`：扫目录下所有 `model*.safetensors`，自解析 header 建 (file, offset) 索引，**与分片数量无关**（所以本地 23 分片 vs pin 的 11 分片无所谓）。注释明写 "no repack required — M0 verified layouts are contiguous"。
- 命名：本地 `language_model.model.layers.N.mlp.switch_mlp.gate_proj.weight`，`parseHeader` 剥 `language_model.` 前缀后正是 `requireExpectedTensors()` 要的名字。

**本地权重实测构成（145.2 GB = 135.2 GiB）**
| 部分 | GB | slotstream 怎么用 |
|---|---|---|
| 专家 switch_mlp | 75.50 (66.7%) | SSD 流式，slot 池 |
| n-gram（在 safetensors，00001-00007） | 32.00 (28.3%) | 按行 pread |
| ngram_table.bin（单独文件） | 32.00 | **mlx-serve 专用副本，完全不读**（内容与上者重复，白占 32G 磁盘）|
| dense trunk | 3.18 (2.8%) | 全常驻（README 说 ~3.8GB，吻合）|
| MTP | 1.63 (1.4%) | 跳过（剥前缀后 `mtp.` 开头）|
| vision_tower | 0.90 (0.8%) | 跳过 |

**兼容性逐项核对（全部通过）**
- 48 层 / 512 专家 / top-10 ✓；`ple_layer_ids=[2]` ✓；`text_config` 存在 ✓
- 专家张量 `shape[0]=512`、单文件内连续（00008-00022）✓
- 9 个 piece 齐全（gate/up/down × weight/scales/biases），`recordBytes = 3,072,000 B = 3.072 MB/专家`
  - gate_proj.weight `[512,640,320]` U32, scales/biases `[512,640,80]` BF16 → 320×32/4=2560, 2560/32=80 ✓
  - down_proj.weight `[512,2560,80]`, scales/biases `[512,2560,20]` ✓
- n-gram shard `[2500012,20]` U32 + `[2500012,5]` BF16 → 160 dims/行, group_size=32 ✓（与 `ngramQGroup` 默认值一致）

**两个要提醒的坑**
1. **`Geometry` 里硬编码 2.76 MB/专家**（main.swift:330 等），本地实际 **3.072 MB**，偏乐观 **+11.3%**。但 `ExpertStore.swift:37` 用 `refs[0].map { $0.rowBytes }` **动态算真实值**，所以 slot 分配是对的；只有 Doctor 显示和 `Planner` 把内存换算成"多少个专家"时会偏乐观（同理 67.9 GB 硬编码 vs 实际 75.5 GB）。`--experts-per-layer` 按 0.133 GB/档 也偏小，实际 0.153 GB/档。
2. **本地是「多模态版」**（`Qwen4ExpForConditionalGeneration`，含 vision_tower + vision_config），slotstream pin 的 pipenetwork 版是纯文本版。**纯文本对话不受影响，但不能看图。**

**其他事实**
- 磁盘可用 323 GB（复用本地则无需额外空间；若 pull 官方版需 104 GB）。
- 项目**未构建**（无 `.build/`）；依赖 mlx-swift 0.31.6+ / swift-transformers / swift-argument-parser，`swift-tools-version: 6.0`，macOS 14+。构建需用户在自己终端跑（Agent 沙箱里 Swift 的 sandbox-exec 会被拦，见 MEMORY.md）。
- `slotstream doctor` **不需要权重**就能跑（只做设备报告 + plan 预览）。
- README 明说**只在 M5 Pro 48GB 一台机器实测过**；128GB M5 Max 是未测路径。48GB+ 后 decode 速度平坦在 ~12 tok/s。
- 定位：对 128GB 机器**不提速**，价值是**把 105GB 常驻内存降到 20-30GB**（释放内存给视频生成等），代价是速度。
